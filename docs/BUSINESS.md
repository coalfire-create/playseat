# 왜 이 앱이 차 안에 있어야 하는가

심사에서 가장 먼저 나올 질문 세 개에 대한 답입니다.
"폰 앱으로 만들면 안 되나", "스포티파이가 이미 하지 않나", "현대가 왜 이걸 넣나".

---

## 1. 폰으로는 만들 수 없는 것

플레이시트의 기능 중 폰 앱이 따라할 수조차 없는 것들입니다. 하나라도 빼면
그냥 또 하나의 공유 플레이리스트가 됩니다.

| 기능 | 필요한 신호 | 폰이 못 하는 이유 |
|---|---|---|
| 앉은 자리로 참여 | 좌석 착석 센서 | 폰은 누가 어디 앉았는지 모릅니다. 물어보면 거짓말할 수 있고, 물어보는 것 자체가 마찰입니다 |
| 운전자 조작 차단 | 기어·주행 상태 | 폰은 지금 이 차가 달리는 중인지, 들고 있는 사람이 운전자인지 모릅니다 |
| 분위기 판정 | 와이퍼 단계, 하향등, 조향 변동폭 | 좌표 기반 날씨 API 는 터널·지하주차장에서 "맑음" 이라고 답합니다. 앞유리에 비가 오는지는 와이퍼만 압니다 |
| 도착 맞춤 편성 | 내비 잔여 ETA | 폰 음악 앱은 목적지를 모릅니다. 그래서 마지막 곡이 늘 중간에 끊깁니다 |
| 분위기 조명 | 앰비언트 조명 제어 | 운전자는 화면을 오래 볼 수 없습니다. 조명은 안 보고도 느껴집니다 |
| 계정 없는 참여 | 착석 + 차량 화면의 코드 | 폰끼리 모이려면 누군가의 계정에 초대돼야 합니다 |

**이 목록이 이 앱의 존재 이유입니다.** 차량 신호를 쓰지 않고 만들 수 있는 부분은
이미 시장에 있고, 우리가 만들 이유가 없습니다.

---

## 2. 스포티파이 Jam·SharePlay 와 무엇이 다른가

| | Jam / SharePlay | 플레이시트 |
|---|---|---|
| 참여 조건 | 호스트와 같은 서비스 유료 계정 | **앉아 있으면 됩니다.** 앱 설치도 계정도 없습니다 (QR → 웹) |
| 누가 넣었는지 | 익명에 가깝습니다 | 좌석이 드러납니다. 차 안에서는 그게 자연스럽습니다 |
| 운전자 보호 | 없습니다 | 주행 중 운전자 화면 조작을 막고 음성만 남깁니다 |
| 환경 반응 | 없습니다 | 비·터널·굽잇길·충전·도착을 차량 신호로 읽습니다 |
| 도착 | 모릅니다 | 마지막 곡이 도착과 함께 끝나게 편성합니다 |
| 독점 | 규칙 없음 | 막지 않고 **지분을 보여 줍니다** |

가장 큰 차이는 첫 줄입니다. 뒷좌석에 앉은 처음 타는 사람이 **아무 가입 없이**
30초 안에 선곡에 참여합니다. 이건 차량 신호가 있어야 가능한 일입니다 —
"그 차에 지금 앉아 있다" 가 곧 인증이기 때문입니다.

## 3. 누가, 얼마나 쓰는가

솔직하게 적습니다. 우리는 현대차그룹의 실제 탑승 인원 데이터에 접근하지
못했습니다. 그래서 숫자를 지어내지 않고, **조건**만 적습니다.

이 앱은 **2인 이상 탑승 구간에서만** 의미가 있습니다. 혼자 타면 그냥
음악 앱이 낫습니다. 그래서 가치가 올라가는 순서는 이렇습니다.

1. **가족 이동** — 주말 나들이, 명절 장거리. 뒷좌석에 아이가 있고, 운전자가
   선곡하느라 화면을 보는 상황이 반복됩니다. 아동 좌석 프로필이 여기서 쓰입니다.
2. **카풀·동료 이동** — 서로 취향을 모르는 사람들이 한 차에 탑니다.
   "아무거나 트세요" 가 가장 자주 나오는 자리이고, 분위기 추천이 그 공백을 채웁니다.
3. **택시·의전·렌터카** — 뒷좌석 승객이 자기 폰으로 넣되 기사 화면은 잠겨 있습니다.
   계정이 필요 없다는 점이 결정적입니다. 승객에게 가입을 요구할 수 없습니다.
4. **충전 대기** — 전기차에서만 생기는, 차 안에 갇혀 있는 20~40분입니다.
   이미 `CHARGING_LOUNGE` 모드로 구현돼 있습니다.

**검증해야 할 것** (이 앱의 가설이 틀릴 수 있는 지점):
- 2인 이상 탑승 구간의 비율과 평균 주행 시간
- 주행 중 헤드유닛 미디어 조작 횟수 — 운전자가 실제로 얼마나 화면을 보는지
- 뒷좌석 승객이 QR 을 찍기까지의 이탈률

세 가지 모두 차량 텔레메트리로 확인할 수 있고, 저희가 가진 데이터로는
확인할 수 없습니다. 적합성 검증이 다음 단계의 첫 항목입니다.

## 4. 수익과 비용

**비용이 거의 들지 않는 구조입니다.**

- 허브(세션 중계·곡 검색)는 지금 개발 편의상 외부 프로세스지만, **차량 안으로
  들어가는 것이 원래 설계입니다.** 세션은 한 차 안에서만 유효하고 바깥으로
  나갈 이유가 없습니다. 그러면 서버 운영비가 0 이 됩니다.
- 저장하는 개인정보가 없습니다. 좌석 번호와 화면에 띄울 이름뿐이고, 하차하면
  지웁니다. 계정·로그인·결제 정보를 받지 않습니다. 개인정보 처리 비용과
  사고 위험이 동시에 사라집니다.

**수익 경로는 셋입니다.**

1. **차량 기본 탑재** — 유료 기능이 아니라 탑승 경험입니다. "뒷좌석도 음악을
   고를 수 있는 차" 는 시승장에서 10초면 설명되고, 체험시킬 수 있습니다.
2. **스트리밍 사업자 제휴** — 플레이시트는 음원을 보유하지 않고 '무엇을 틀지'
   만 정합니다. 사업자에게는 **차량 안 재생 세션의 유입구**가 됩니다.
   뒷좌석 승객 n 명이 자기 취향을 입력하는 자리는 추천 데이터로서도 가치가 있습니다
   (단, 개인 식별 없이 좌석 단위로만 — 위 구조를 깨지 않는 선에서).
3. **드라이브 앨범** — 이동 1회가 하나의 기록으로 남습니다(이미 구현).
   이 기록이 재방문 이유를 만들고, 음원 서비스로 내보낼 수 있는 플레이리스트가 됩니다.

## 5. 단계별 연동 계획

지금 무엇이 되고 무엇이 안 되는지를 섞지 않고 적습니다.

**1단계 — 지금 (제출 시점)**
- 차량 신호: Pleos Vehicle SDK 연동 완료 (좌석·기어·충전·와이퍼·전조등·조향).
  내비 ETA 는 NaviHelper `onDrivingInfo` 연동 완료.
- 재생: **실제로 소리가 납니다.** 공개 API 의 30초 미리듣기를 허브가 중계해
  차량이 재생합니다. 오디오 포커스와 MediaSession 을 정식으로 씁니다.
- 음원: **전체 음원은 보유하지 않습니다.** 미리듣기 30초라는 한계를 화면에
  그대로 표시합니다.

**2단계 — 사업자 음원 연동**
- `PlaybackGateway` 인터페이스 하나만 교체하면 됩니다. 세션 로직·UI·폰은
  재생 방식을 모릅니다. 이 경계를 처음부터 둔 이유입니다.
- 음원 라이선스는 기존 스트리밍 사업자가 그대로 보유합니다. 우리는
  '누가 무엇을 들을지 결정하는 레이어' 만 맡습니다.

**3단계 — 허브를 차량 안으로**
- 세션 중계와 곡 검색을 차량 앱 내부 서비스로 옮깁니다. 외부 서버가 사라지고,
  차량 Wi-Fi 안에서만 동작하므로 통신비·운영비·개인정보 위험이 모두 없어집니다.
- 좌석 센서가 없는 차량을 위해 안전벨트 체결 폴백이 이미 들어가 있습니다.

## 6. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 음원 라이선스 | 음원을 보유하지 않는 구조. 재생을 사업자 세션에 위임하고 우리는 결정 레이어만 맡습니다 |
| 주행 중 주의분산 규제 | 주행 중 운전자 화면은 목록·검색·키보드를 걷어내고 터치 타깃을 2개로 줄입니다. 매니페스트 `distractionOptimized` 선언의 전제를 코드가 지킵니다 |
| 좌석 센서 비탑재 차량 | 안전벨트 체결 신호로 폴백. 둘 다 없으면 좌석을 수동 선택하게 열어 둡니다 |
| 분위기 판정이 틀릴 때 | 판정과 **근거 문장**을 같이 보여 줍니다. 틀렸다는 걸 사람이 알 수 있어야 고칠 수 있습니다 |
| 한 사람의 독점 | 막지 않고 지분을 보여 줍니다. 그래도 불만이면 스킵 투표(과반·최소 2표)가 있습니다 |
| QR 사진으로 무단 참여 | 차량 화면에만 있는 네 자리 탑승 코드 + 착석 센서. 앉아 있고 차 안 화면을 볼 수 있어야 참여합니다 |
